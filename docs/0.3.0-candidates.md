# 0.3.0 feature candidates

Working document for the 0.3.0 cycle. Everything here follows the repo's
standing rule: **a claim without a command that reproduces it is an opinion.**
Each entry states what evidence exists today and what evidence would move it
from candidate to committed — or kill it.

Status legend:

- **COMMITTED** — already promised in a shipped release's public record, or
  confirmed by the maintainer for this cycle.
- **PROPOSED** — has a design document; being developed toward a decision
  this cycle.
- **EXPLORATORY** — captured as a foundation for exploration; not yet
  carrying a design detailed enough to evaluate against the evidence bar.
  Promotion path: triage → design document → PROPOSED → evidence → decision.
- **REFERENTIAL** — captured with its evidence bar and kill criteria, but not
  scheduled for this cycle unless something makes it pressing. Kept so the
  analysis is not redone from scratch when it is picked up.
- **REJECTION STANDS** — measured or reasoned out in a previous cycle; listed
  so nobody re-proposes it without new evidence.

Version class: 0.3.0 is the **breaking slot** under pre-1.0 semver (the minor
position is the breaking one below 1.0 — see RELEASING.md). Item 1 alone
justifies the bump; everything else must be additive or breaking-with-cause.

No `release/0.3.0` branch exists yet, deliberately. Per RELEASING.md the
release branch is cut from master when the release is actually assembled;
cutting it at planning time would only create a long-lived branch to keep in
sync. This document rides an ordinary feature branch.

## 1. Remove the deprecated panicking constructors — COMMITTED

Maintainer-confirmed for this cycle (2026-08-11), on top of the standing
public commitment: `SeqRing::{producer, consumer}` and
`EventBuf::{producer, consumer}` were deprecated in 0.2.0 with removal
scheduled for 0.3.0. That schedule is public
in the 0.2.0 changelog, README, AGENTS.md, and the rustdoc deprecation notes.
Rationale is on record: on the targets this crate exists for, a panic is a
reset, and a code-size probe showed no panic strings reach the binary when
only the `try_*` constructors are used.

**Evidence in hand:** the deprecation shipped; `try_producer`/`try_consumer`
have existed since 0.1.4 and are the documented path everywhere.

**Coupled edits the compiler will not enforce** (from AGENTS.md, gathered here
so the removal PR can be checked against the list):

- Delete the four methods and their rustdoc.
- Drop `#![allow(deprecated)]` from the test modules in `seq_ring.rs`,
  `event_buf.rs`, and `traits.rs` — it exists only because the old API needed
  coverage while still public.
- Remove or convert tests that exercise the panicking API
  (`double_producer_panics`, `double_consumer_panics` — the SPSC-enforcement
  property they pin must be re-pinned on the `try_*` path, which returns
  `None` rather than panicking).
- `src/loom_tests.rs:19` notes the deprecated paths' orderings still need
  proving "until 0.3.0" — retire or retarget those models at removal.
- Update test counts in README.md and AGENTS.md (Coupled-edits table).
- README `unsafe`/SPSC note at line ~220 references the 0.3.0 removal —
  rewrite it in past tense.
- Changelog entry under `### Removed`, marked **Breaking**.
- Re-run `./scripts/codesize.sh` — removal should shrink or hold every row;
  shrinkage is a re-bless nudge, never a failure. Re-bless deliberately.
- Full matrix: `./scripts/ci.sh`, `./scripts/miri.sh`, `./scripts/loom.sh`
  (public-API surface changes; Loom models change with it).

## 3. `LatestBuf` — freshness-first SPSC snapshot channel — PROTOTYPE / EVALUATING

Design document received 2026-08-11 and captured in full at
[`docs/proposals/latest-buf.md`](proposals/latest-buf.md). This section is
the cycle-tracking summary; the proposal is the reference.

**What it is.** A three-slot exclusive-ownership SPSC channel that retains
only the latest complete publication (or latest complete block). At every
instant one slot is producer-owned, one consumer-owned, one held by an atomic
exchange state; ownership transfers *before* access, so producer and consumer
never touch the same bytes. Both operations are at most a single atomic
`swap` (an empty poll is answered by one `Acquire` load — A.1) — no
CAS retry loop. Overload appears as observable replacement
(`PublishReport::replaced_unread`), consumer-side loss as an observable gap
(`LatestItem::skipped`).

**Why it matters here.** It targets the same freshness-first niche as
`SeqRing` — producer never waits, stale data is droppable, loss is counted —
but with a soundness argument built on ownership instead of a seqlock's
post-hoc validation, so it should pass Miri **with the race detector on**.
`SeqRing` stays; this is a complement with different semantics (latest-value
snapshot vs ordered recent window), not a replacement. The proposal's own bar
for ever calling it a `SeqRing` replacement is an open question, not a goal.

**Semver class:** additive only — a new type, and possibly new traits
(`LatestSink` / `LatestSource`); `Sink`/`Source`/`Link` unchanged. It does
not depend on the 0.3.0 breaking slot, which decouples its schedule from
item 1 if the evidence takes longer than the cycle.

**Against the bar:**

- *Predictability:* improves the story — wait-free producer, bounded
  consumer, observable replacement and gaps, and a primitive in the
  freshness-first niche with no formal data race. The proposal deliberately
  claims falsifiable operation counts, not "fast" (§15).
- *Efficiency (evidence required):* `codesize.sh` across all gated targets;
  the hazard rows are thumbv6m / ESP32-S2, where the atomic `swap` becomes a
  portable-atomic critical section — the proposal itself asks whether a
  bounded critical-section implementation beats atomic exchange on
  single-core targets (§22), and that question is answered by measurement,
  not preference. Memory cost is fixed but real: three payload slots, and
  three complete *blocks* in the block variant — must be stated per target
  in the docs, never hidden.
- *Cycles:* `publish` and `take_latest` must measure constant with respect
  to lag and occupancy in the reference environment, and get compared
  against the existing `EventBuf`/`SeqRing` rows.
- *Regression resistance:* Loom models of the exchange state machine
  **before** optimisation (adoption sequence §21 fixes this order);
  ordering-mutation runs proving the models catch a weakened `AcqRel`; the
  Miri detector-on pass is itself the feature, so it must be pinned in
  `scripts/miri.sh`'s full-checking pass or it will drift; generation-wrap
  tests (zero reserved, wrap-aware gap arithmetic — §18).
- *Ergonomics:* decided last. `static_spsc!` extension, trait placement, and
  the `Source<T>` question (§13) all wait on the primitive existing. The
  §13 analysis already applies this repo's `RingBuf::pop` rejection
  correctly: no `Source` impl that silently discards the skipped count.

**Sequencing (per the proposal's §21, condensed):** contract → prototype →
Loom → Miri → ordering mutation → codesize + cycles → sample-vs-block
decision → traits only with the primitive that needs them → harness
integration.

**Cycle state (2026-08-11):** step 1 is drafted — the semantic contract
lives at [`proposals/latest-buf-contract.md`](proposals/latest-buf-contract.md)
with clause IDs, an evidence map, and three decision points (D1 wrap policy,
D2 `Source<T>` policy, D3 sample-vs-block), initially **deferred open by
maintainer decision (2026-08-11)** and each since closed on the record the
same day. **D1 closed** as options (a) + (c): exact within one wrap
span, the documented under-counting formula beyond, with count-critical callers
pointed at a wider payload sequence or a saturating counter; the wrap family
(C3/C5/O2) and new non-promise X6 carry the beyond-span text and the honest
adopter disclosure. **D2 closed 2026-08-11** as the proposal's option 1: no
`Source<T>` impl — the maintainer's articulation on the record is that
`LatestSink`/`LatestSource` were designed as the contract surface for the
type, solving what the existing traits structurally could not; non-promise
X7 states the substitution limitation and the adapter escape hatch, with a
compile-fail pin so the decision cannot regress silently. **D3 closed
2026-08-11** as the convergent answer: payload-agnostic `LatestBuf<T>`,
complete blocks as payloads via the BlockBuf composition, no separate
`LatestBlockBuf`; the joint composition matrix at `8593b4a` is the
acceptance measurement set for both shapes. All three contract decision
points are now closed. **A.3 closed 2026-08-11** as channel-resident role
state with stateless handles — the same sole-role doctrine decision H
ratified, on the full-column evidence (both cross-context role-handoff Loom
models, all four role-handoff mutation detections); persist-on-drop is
considered-and-not-selected with its partial evidence preserved in the
evaluation record, and new contract non-promise X8 states the role-recovery
boundary for integrators without prescribing their architecture. Every
LatestBuf decision is now closed, and the proposal's three Appendix A
review caveats are all resolved: **A.1** measured and selected (the
`Acquire`-load empty-poll fast path), **A.2** validated by the
wrap-boundary unit set, and **A.3** closed as above. Development is no
longer paused: the lane's prototype and complete admission evidence live
on `candidate/latest-buf` (draft PR #35). The live comparison record is
[`proposals/latest-buf-evaluation.md`](proposals/latest-buf-evaluation.md);
the 11-target code-size, pinned-cycle, A.1, and RAM results are in
[`proposals/latest-buf-measurements.md`](proposals/latest-buf-measurements.md);
the joint complete-block matrix is in
[`proposals/latest-block-composition-measurements.md`](proposals/latest-block-composition-measurements.md)
(171-6,958 reference instructions across the 2/8/16-byte by 8/32/128 grid,
136-8,280 bytes combined channel/builder RAM). The lane now waits on
acceptance review, not on decisions or development. Traits `ObservedSource`
and the payload metadata traits remain explicitly gated on a *second*
implementation proving the vocabulary honest — they are not part of the
initial acceptance question.

**Composition evidence is deliberately deferred.** Hardware-in-the-loop
evaluation of the full producer→transport→consumer composition is the last
mile of the argument — valuable, target-specific, and sequenced *after* the
soundness (Miri/Loom) and cost (codesize/cycles) evidence. It is never an
implementation prerequisite and never a substitute for the memory-model
proof. (Maintainer decision, 2026-08-11: the framing stays; no specific
harness is named or depended on.)

**Kill criteria:** flash or interrupt-latency cost on thumbv6m/ESP32-S2 that
cannot be brought inside what the codesize gate tolerates for a new row;
or Loom/Miri failing to validate the ordering sketch after honest attempts —
the proposal says the sketch "must be validated rather than accepted," and
that cuts both ways.

**Relationship to C1 (referential):** `LatestBuf` covers the race-free need
for *latest-value* consumers with general `T: Copy` payloads — strictly
broader than C1's word-sized restriction on that axis. C1 remains referential
for the distinct case of a race-free *ordered recent window* (in-order
draining of a backlog), which `LatestBuf` deliberately does not provide.

## 4. Bounded-handoff taxonomy — EXPLORATORY

Comprehensive exploratory document received 2026-08-11 and captured in full
at [`docs/proposals/exploratory-primitives.md`](proposals/exploratory-primitives.md).
It frames the crate's broader opportunity — a small collection of explicitly
bounded handoff mechanisms, never a general event bus or executor — and
requires every primitive to answer four questions: what is retained, what
happens under overload, which context owns each piece of memory, and what
bounds can be measured. Its admission rule and out-of-scope list are adopted
as the standing filter for everything below.

These entries begin **EXPLORATORY**: captured for triage until their contract
and evidence bar are complete. `LatestBuf` is already PROPOSED with a contract
(§3), and `EventFlags` has now reached PROPOSED on its candidate branch; their
taxonomy entries cross-reference the completed design packages.

**Update (2026-08-11):** each Tier 1/2 primitive now has its own
exploratory design document under `docs/proposals/`, seeded with the
substantive text moved out of the taxonomy plus its triage notes, open
questions, and promotion bar. A document existing does not itself make a
design ready; promotion to PROPOSED happens only after its contract and
evidence bar are complete. EventFlags is the first primitive promoted from
this set.

### Initial triage (2026-08-11)

Tiered per the document's own suggested exploration order, with collision
and promotion notes from this repo's record. Tier placement is a starting

**Tier 1 — nearest-term, candidate for the next design document:**

  D3* on the LatestBuf contract (sample-vs-block first deliverable): a

  the implementation, ordering proof, code-size/cycle tables, and exact
  interrupt-masked windows are in
  [`proposals/event-flags.md`](proposals/event-flags.md). The candidate keeps
  SPSC `Send + !Sync` role handles, uses one Release `fetch_or` and one Acquire
  `swap(0)`, and deliberately does not implement the stream traits. Measured
  portable paths mask interrupts for 4 instructions on thumbv6m and 5 on
  ESP32-S2; the measured ESP32-S3 target instead emits native `s32c1i` and
  masks for 0 instructions.
- **`CountedSignal`** (saturating per-condition counter) — design
  document: [`proposals/counted-signal.md`](proposals/counted-signal.md);
  clause-numbered contract:
  [`proposals/counted-signal-contract.md`](proposals/counted-signal-contract.md).
  Same niche and same triage notes as `EventFlags` (cross-referenced, not
  duplicated); the saturate-don't-wrap rule matches the `dropped_accum`
  convention already in the codebase. Separate design documents by
  maintainer direction, with the handle-model question explicitly shared —
  one answer for both. **Shared decision H (2026-08-11):** both lanes use
  sole-role handles that are `Send + !Sync`, with `&self` operations; any
  future MPSC signal is a separate type with separate evidence.
  **CountedSignal lane update:** promoted to PROPOSED after applying H,
  freezing its clause-numbered contract, and completing the
  unit/Loom/Miri/code-size/reference-QEMU evidence map.

**Tier 2 — high value, hard problems named, needs design work:**

- **`SlotPool`** (zero-copy ownership-state transfer) — design document:
  [`proposals/slot-pool.md`](proposals/slot-pool.md). Named as the
  foundation `BlockBuf` and future primitives could build on.
  *(Outcome: evaluated in full on `candidate/slot-pool`, then **deferred**
  by decision S below — evidence banked, adopter-gated trigger
  registered.)* Two triage
  flags beyond the document's own difficult-areas list: (a) grants/claims
  imply **non-`Copy` payloads and RAII drop behaviour** — a genuine

  (b) the `ReservableSink`/`ClaimSource` sketches use GATs — fine at MSRV
  1.92, but the grant lifecycle (commit-or-cancel, no unbounded reservation

**Tier 3 — deferred by the document's own reasoning (concrete adopters
first):**

- **`FanoutRing`** — the document itself recommends starting with the

  multi-consumer ring, and deferring until two real consumers prove
  duplicated queues are an actual cost. Adopted as the triage position.
- **`PriorityBuf`** — composition helper over existing `EventBuf`s first;
  a new low-level queue only if composition measurably fails. The

- **Count-based rate adapters** (`EveryNth`, block-forming, tick-latest) —

  document's caveat that closure-based adapters must not inherit the
  crate's determinism claims by trait implication belongs in AGENTS.md if
  any adapter ships.
- **Deadline-aware consumption** — caller-supplied time only,
  `max_discards`-bounded; keeps the no-clock rule.
- **Request/response pairing** — composition of two bounded channels,
  single-requester/single-service first; no new synchronization algorithm.

### Cycle decisions P and S — CLOSED (maintainer, 2026-08-11)

**P — BlockBuf publication foundation: Copy composition**, for the shapes
this cycle supports. The budget posture is deliberate: **no single
library-wide threshold is claimed — the per-shape measured rows are the
budget statement**, consistent with the measurement record's refusal to
invent one. Accepted completion + publication spans 159–8,658 reference
instructions across the 2/8/16-byte × N = 8/32/128 grid, bounded and
linear in block bytes; the only measured context where the copy plausibly

multiple producer/consumer integrations."* Domain behaviour belongs in the

pub/sub routing, serialization, DSP, DMA cache maintenance, …) is the

### Crate identity (maintainer articulation, 2026-08-11)

The taxonomy sharpened what ph-eventing is trying to do, and the maintainer's
formulation is recorded here so it survives the cycle:

> ph-eventing removes a maintenance grenade from the producer and consumer
> crates. It lets an IMU driver be an IMU driver and a DSP library be a DSP
> library, while the messy coupling layer between them is owned by one crate
> designed specifically around the standing principles — predictability,
> determinism, measurable cost — and able to *demonstrate* them. Just as
> important is what it is not and must not creep into becoming: the
> out-of-scope list is a load-bearing filter, keeping the crate a narrow
> band of primitives that solve specific integration tasks for MCUs that
> require that determinism.

**Follow-up doc task for this cycle:** promote this framing into the
permanent surfaces when 0.3.0's docs are refreshed — the "What this crate
optimises for" section of AGENTS.md (which currently states the priority

positioning, extending the 0.2.0 metadata rework that already moved the
description from "ring buffers" to determinism. The admission rule and the
out-of-scope list go with it, so the filter binds future proposals from the
canonical agent reference, not from a cycle document.

## Referential candidates — analysed, not scheduled

C1–C3 are **REFERENTIAL** for this cycle (maintainer decision, 2026-08-11):
the analysis and evidence bars below are kept current so any of them can be
promoted without redoing the groundwork, but none is being developed for
0.3.0 unless it becomes pressing.

### C1. Race-free word-payload overwrite ring

The `seq_ring` module docs name the alternative that was passed over:
*"a ring restricted to a word-sized payload could hold it in an atomic and
would be **fully race-free**"* — generality (`T: Copy`) was chosen over formal
soundness. That trade was right for the general type, but nothing prevents
offering the narrow type **alongside** it: an overwrite ring whose payload is
`u32` (or anything with a lock-free atomic representation), with the same
producer-never-blocks contract and a clean bill from Miri's race detector.

Who it serves: users for whom the documented seqlock deviation is a
compliance or tooling blocker (their own `cargo miri test` flags our crate
today — the 0.2.0 Known Issues call this out explicitly) and whose telemetry
payload fits a word.

- **Predictability:** strictly improves — removes the one formal deviation
  for users who can take the payload restriction.
- **Efficiency (evidence required):** `scripts/codesize.sh` on all targets.
  The hazard rows are thumbv6m / ESP32-S2, where portable-atomic turns every
  RMW into an interrupt-disable critical section — an atomic-payload design
  may cost *more* there than the seqlock it replaces. One target is not
  evidence; the try_split lesson applies verbatim.
- **Cycles:** add probe regions; `push` must stay constant empty-vs-loaded.
- **Regression resistance:** new Loom models (capacity 2, tiny) + Miri pass
  with the race detector **on** — that detector-on pass is the feature, so it
  must be pinned or it will drift.
- **Ergonomics:** naming and whether it is a new type or a parameterisation
  of `SeqRing` decided last, and at compile time.

**Kill criterion:** if the thumbv6m/S2 flash or latency cost exceeds the
seqlock version's by more than the +16-byte gate allows and cannot be
recovered, ship it feature-gated or not at all — do not absorb the cost into
the default build.

### C2. Sequence-wrap extra-drop realignment

Known issue since 0.1.4, restated in 0.2.0: once per `u32` wrap, `SeqRing`
drops extra entries because `push` skips the reserved sequence `0`, so the
slot walk only realigns when `N` divides `2^32 - 1` (a power-of-two `N` drops
exactly one; `N = 96` drops 33). Documented as a data-loss bound, not a
soundness issue.

Candidate: make the wrap lossless (or uniformly drop-one) for every `N`, e.g.
by skipping a full slot-cycle-aligned block at the wrap instead of the single
reserved value, so producer and consumer mappings stay in phase.

- **Predictability:** improves a documented bound; the current behaviour is
  already bounded and reported, so this is refinement, not repair.
- **Efficiency (evidence required):** the wrap check sits on the push path.
  `scripts/cycles.sh` must show `SeqRing::push` unchanged (34/33) — a hot-path
  instruction added for a once-per-4-billion event is a bad trade on its face.
- **Regression resistance:** the wrap tests
  (`lag_across_wrap_counts_drops_exactly`, `consumer_skips_reserved_seq_zero_on_wrap`,
  `push_wraps_seq_from_zero_to_one`) change with the semantics; the
  `read + dropped` invariant must be re-proved per branch. Miri 32-bit pass
  mandatory (it caught the last wrap-adjacent bug, `dropped_accum` overflow).
- **Semver:** behaviour a caller could rely on changes → breaking, which is
  fine in this release and only this release.

**Kill criterion:** any measurable hot-path cost, or any complication of the
`push_inner` commit order — the order *is* the correctness argument, and a
cleverer wrap is not worth touching it for a once-per-wrap bound that is
already documented and counted.

### C3. Cycles baseline gate inside the reference environment

AGENTS.md records that the old blocker for gating instruction counts is gone
(probe lockfile committed, QEMU pinned in the reference image) and names what
is still missing: *"a committed baseline file with a bless flow like
`codesize.sh`'s."* The counts are deterministic per environment now — 0.2.0
proved it — so the gate is buildable, with the same asymmetric rules
(growth fails, shrinkage reports, SKIP exits 2, missing row fails,
`--bless` refuses after a partial run).

Scope discipline: the gate runs **only inside `verify.sh`** (the reference
image), never in `ci.sh` — the QEMU-availability reasoning in AGENTS.md
stands, and reversing it would be an explicit decision, not a side effect.

- This is regression resistance (priority 3) for the crate's headline claim:
  the 0.2.0 release notes lead with "measured instruction counts instead of
  adjectives," and today nothing stops those numbers regressing silently
  between releases.
- **Evidence required:** two independent runs of the gated flow in the
  reference image producing identical verdicts; a forced regression (add a
  nop to a marker region) must fail loudly — prove the negative path fires,
  don't just watch the happy path pass.

**Kill criterion:** none foreseeable on cost (it adds no runtime code and no
`ci.sh` burden); dies only if the determinism claim fails replication.

## Rejections that stand

- **`RingBuf::pop` + `Source`.** Rejected on predictability: `push` still
  overwrites, so the type would advertise `Source` while losing data that
  `forward` structurally cannot report. Re-open bar: a design that makes the
  loss reportable (a drop counter changes `RingBuf`'s no-atomics,
  single-owner character — that cost would need its own measurement).
- **`try_split()`.** Rejected on measurement: ESP32-S2 +59% and Cortex-M0+
  +43% flash on the existing bring-up path to save 4–16 bytes on
  well-provisioned cores. Re-open bar: a new implementation measured cheaper
  in the reference environment across **all** gated targets — a win on
  Cortex-M4 alone was exactly the mirage last time.
- **Anything that adds a runtime dependency, allocation, or a panic on a hot
  path.** Not a 0.3.0 rule, a permanent one; restated because a breaking
  release is when such proposals tend to arrive.

## Non-goals for 0.3.0

- MSRV bump: no candidate requires one; an MSRV move is breaking and needs
  its own justification, not a ride-along.
- MPSC/MPMC variants: out of scope for the SPSC design; nothing in the
  evidence base motivates them this cycle.
- Changing the seqlock design of `SeqRing` itself: the deviation is
  documented and deliberate (C1 offers the race-free alternative *beside* it,
  not instead of it).

## Cycle mechanics — the way ahead (2026-08-11)

How this cycle facilitates independent development *or rejection* of each
candidate while integrating cleanly. Every rule below traces to a specific
0.2.0 scar; the scar is named so the rule survives being questioned.

### Structure: independent PRs, decisions before branches

1. **This planning branch merges to master first.** The proposals, the
   contract, and the taxonomy become the single canonical record every
   candidate branch forks from. Divergent copies of the shared planning
   docs are the first integration hazard to kill.
2. **One candidate, one branch, one PR — never stacked.** *(Scar: a
   seven-deep 0.2.0 stack cost four conflict resolutions from one
   mid-stack commit; children silently build on a stale parent until
   GitHub flags DIRTY.)* The candidates are additive and orthogonal — new
   modules, new files — so independence is natural, not aspirational.
3. **Dependencies are sequenced by decision, not by branch.** Where real
   coupling exists, resolve the *decision* on the planning record before
   opening the implementation branch: D3 before BlockBuf implementation;
   the SlotPool-standalone-vs-via-BlockBuf question before either codes
   against the other; the EventFlags/CountedSignal handle-model answer
   once, for both. No branch waits on another branch — only on a decision.
4. **Item 1 (deprecation removal) proceeds immediately as its own PR.** It
   depends on nothing, everything in the release depends on it existing,
   and its coupled-edit checklist is already written (§1).

### Integration surfaces: the known conflict magnets

5. **Changelog:** every PR adds its entries under `## Unreleased`; the
   heading closes only in the final pre-tag commit on the release branch.
   *(Scar: closing it while sibling PRs were open turned every one
   CONFLICTING.)*
6. **Coupled shared files:** each primitive PR touches `src/lib.rs`
   exports, the `Cargo.toml` `include` allowlist (a missed entry ships a
   crate that cannot build), README/AGENTS test counts, and possibly the
   codesize baseline. Merge upstream-first; after any candidate merges,
   sync the others immediately rather than at review time.
7. **New probe/model directories get ignore rules BEFORE first build, and
   staging is always explicit paths.** *(Scar: `git add -A` swept ~500
   build artifacts into commits four separate times; every new probe
   workspace reintroduces the hazard on day one.)* New scripts also get
   `git update-index --chmod=+x` — the executable bit does not commit
   from Windows.
8. **Codesize baseline rows are added per accepted primitive via a
   deliberate `--bless`, with the diff reviewed** — never re-blessed
   reflexively to green a run.

### Evidence: what a candidate PR must carry

9. **A PR is not opened until its contract exists and its evidence map is
   implemented** — the design documents' promotion bars (each doc §"
   Promotion bar") are the gate between EXPLORATORY and a PR. Measurements
   ride in the PR body: codesize across all gated targets, cycles in the
   reference environment where bounded cost is claimed, Miri/Loom for
   anything lock-free. *(Scar: one-target evidence — `try_split` looked
   like a clean win on Cortex-M4 and lost 43–59% on the constrained
   cores.)* A SKIP in any run is not a pass.
10. **Rejection is a first-class outcome with the same paper trail.** A
    candidate killed by its numbers gets a REJECTED status header on its
    design document with the evidence attached, a worked-rejection entry
    where the reasoning teaches (the AGENTS.md pattern), and its branch
    archive-tagged, not deleted. *(0.2.0 shipped two rejections as
    features of the release notes; that is the standard.)*
11. **Counter-agent review per the 0.2.0 arbitration protocol** on every
    PR: verify each finding against the tree, prove or disprove rather
    than argue, reply then resolve, re-trigger after each fix batch, stop
    when severity converges to nits. After any rewrite, grep every doc
    surface for now-false claims. *(Scar: six instances of correct text
    added beside the stale text it should have replaced.)*
12. **Every type carries an engineering record at `docs/records/<type>.md`**
    (maintainer decision, 2026-08-11; template and rules in
    [`records/README.md`](records/README.md)). The record is the executive
    briefing over the normative sources — a short value statement, then
    risks and integration concerns in integrator terms, then each
    technical claim mapped to its validating evidence, then the working
    record (decisions, measurements, proof narrative, rejected
    alternatives). It is an enduring engineering record, not rustdoc
    duplication: rustdoc says how to use the type; the record says why it
    is trustworthy and what it cost. **A lane's record is part of its
    acceptance package — no type is accepted without one.** The 0.2.0
    types receive theirs when next materially touched. Records obey the
    stale-claims discipline (rule 11).

### Assembly: unchanged from RELEASING.md

12. `release/0.3.0` is cut from master only when the accepted set has
    merged. Version bump and changelog-heading close travel in the same
    final pre-tag commit; the full matrix runs in the reference
    environment (a fresh frozen image tag for the release); explicit
    staging; publish per the checklist.
13. Every acceptance or rejection gets its reasoning recorded — AGENTS.md
    for design rules, the changelog for shipped behaviour — because on
    this crate the measurement discipline is the feature.
